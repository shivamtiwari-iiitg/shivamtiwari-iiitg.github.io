01 Messaging & realtime

Two chat surfaces, two completely different transports — because 1:1 and 1:N are different problems.

P011:1 Direct Messages over SSEShareChat
The hook. Direct messages run over a dedicated Server-Sent-Events connection — one persistent stream per device, backed by a Room cache — with delivery and read receipts as a separate REST handshake, not carried on the SSE channel. Push in, pull/batch out.

Architecture:

SEND path:
  POST chat/v1/sendMessage  (DMService)
    → builds MessageModel
    → on success pushes UpdateChatListModel to refresh conversation-list preview

RECEIVE path:
  InitRtcManagerUseCase
    → appRtcEventsManager.initialiseAndConnect()
    → opens stream at $rtcGatewayUrl/sse over SHARED OkHttp client
    → lifecycle-aware disconnect when backgrounded
    → filtered by AppRtcMessageType.SC_DM_EVENT

ACK path (deliberately asymmetric — REST, not SSE):
  handleNewMessage() decides READ vs DELIVERED
    (based on whether chat screen is foregrounded)
    → queues ack into chat_pending_report Room table
    → retry loop drains via POST chat/v1/updateChatStatus

Message status ladder: -2 retry · -1 sending · 0 deleted · 1 sent · 2 delivered · 3 read. Room cache is three tables behind one ChatDao: message_entity, chat_list_entity, chat_pending_report.

Message-request split: INITIATE(0) → UNKNOWN(1) → KNOWN(2), plus SHAKE(3)/DELETED(5). Both fragments hit the same chat/v1/getChatList parameterized by knownChat: Boolean. Promotion is one-directional — replying is the accept, there's no explicit accept button.

Hardest problem — SSE drop mid-conversation. ReconnectRtcManagerUseCase reconnects, but missed messages recover via REST history refetch, not stream replay. The mental model that makes this correct: SSE is a live-tail; Room + REST is the source of truth. If you treat the stream as the source of truth you have to solve replay, ordering, and gap detection on the wire — treating it as a tail means a reconnect just triggers a normal fetch.

Archaeology detail worth volunteering: the subscription disposable in DmPresenter is still named mMqttSubscribtionDisposable — a leftover from before the SSE migration. It's a good answer to "has this system changed over time?" precisely because it's checkable rather than a story.

What I'd change: DeliveryReport is a single triplet. For small group DMs (3–10 people) it would need to become a per-recipient map.

P02Group chatroom — Firestore fan-out + Agora live audioShareChat
The hook. Same "chat" surface as DMs, entirely different transport — because it's 1→N broadcast, not 1→1. The client posts over REST, the server writes one shared Firestore document, and Firestore's own replication fans it out to every listener including the sender. Live audio is a third layer: Agora carries the media, Firestore stays the control plane.

Text path:

Client → REST postMessageToServerC(...)
       → server writes Firestore doc
       → every participant's addSnapshotListener fires (incl. sender)

Infrastructure detail: a DEDICATED secondary Firebase project —
  TertiaryFirebaseFireStore, app instance "chatroomMumbaiRegion",
  separate from the primary project.

FireStoreDocumentAndCollectionHandler wraps the listener in a
coroutine callbackFlow; a custom JsonDeserializer reads an `action`
field to pick the model (CHAT_TEXT_MSG → CommentRealTimeModel).

Dedup is mandatory, and the reasoning is the interesting part. Snapshot listeners double-fire — the optimistic local echo plus the server-confirmed snapshot. ChatRoomCommonData keeps a messageIds: HashSet<String> checked in handleCommentsRTE(). That set is plain and unsynchronized — and correct anyway, because every mutation runs inside a serialized Orbit intent{}. Same lock-free-by-construction reasoning as the interventions actor below.

Live audio as a dynamic feature module:

:feature:agoraudio sits in AGP's dynamicFeatures block
  → base APK ships NONE of Agora's SDK classes or native .so libs

Base app compiles against ShareChatAgoraBridge / AudioAdapter
  → Dagger binds NoOp impls (Completable.complete(), empty flows, -1)
    so nothing crashes mid-download
  → once installed, NoOp classes reflectively:
    Class.forName("sharechat.feature.agoraudio.audio.AgoraAudioImpl")
    and swap in the real engine
  → reaching back into base Hilt graph via @EntryPoint
    (AgoraModuleDependencies)

Token lifecycle — no audio interruption: join tokens arrive pre-baked inside the Firestore seat payload (agoraPublisherToken/agoraSubscriberToken). onTokenPrivilegeWillExpire (~30 s warning) and onRequestToken trigger a REST renew, then rtcEngine.renewToken() updates in place. No leave/rejoin cycle.

Profile is LIVE_BROADCASTING, not COMMUNICATION — seats get promoted to CLIENT_ROLE_BROADCASTER, everyone else stays CLIENT_ROLE_AUDIENCE. That's the right shape for one host and hundreds of listeners. Sync direction is strictly one-way: Firestore seat event → Agora API call, because Agora has no independent concept of a room-wide "muted" state; mute only affects the local outgoing stream.

Raise this unprompted — the auth gap. The Firestore connection carries no per-user Firebase Auth identity — there's no signInWithCustomToken anywhere in the chatroom module. TertiaryFirebaseFireStore.createFirestoreInstance() initializes from bare FirebaseOptions delivered by the session-authenticated room-entry REST call. The real gate is that REST call; once you hold the credentials, fine-grained access has to live in server-side Security Rules keyed on something other than request.auth.uid. Flagging this yourself is worth more than any answer given after being asked.

Also honest: ordering leans on Firestore surfacing one write per callback (there's no sort by createdOn); there's no confirmed backfill path re-triggering fetchMessagesV2 on reconnect; and no retry/backoff around postMessageToServerC equivalent to DM's chat_pending_report. None are confirmed bugs — they're the questions I'd ask the owning team before shipping near it.

What I'd change: mint per-user Firebase custom tokens at room entry, so Security Rules can key on real identity.

02 Platform & framework

Systems other teams build on — where API design is the actual product.

P03Interventions Framework — cross-screen arbitration engineShareChat
The hook. A cross-screen arbitration engine for in-app messaging — app-rate prompts, permission asks, tooltips, onboarding nudges. The backend sends a prioritized ordered list; a single actor coroutine holds that list plus every visible screen's eligibility rules and, on each state change, shows the first candidate that's both eligible and has a resumed handler. One intervention active at a time app-wide, and no locks anywhere.

Module structure — strict one-way dependency:

feature → repository → manager → model

  model      : no opinions (pure data)
  manager    : no I/O
  repository : no UI
  feature    : no queueing logic

Each independently testable — InterventionManagerTest,
InterventionsRepositoryImplTest, fakes for the layer below.

The actor: InterventionManagerActor is a kotlinx.coroutines.channels.actor — one serialized loop, ten intents covering the whole lifecycle:

AddHandler / RemoveHandler / PauseHandler
OfferConfig / OfferUiState
ShowIfEligible / OnTimedOut / ClearAndMoveNext
GetActiveIntervention  (via CompletableDeferred)

The public singleton only ever does:
  coroutineScope.launch { intentActor.send(intent) }

Side effects exit through a SEPARATE channel
  (InterventionSideEffect.RecordInterventionStatus)
  so the actor never blocks on disk writes or analytics.

Two nested MVI mechanisms coexist: a hand-rolled channel actor for the queue, and Orbit MVI (ContainerHost/intent{}/reduce{}) for the surrounding app-state containers.

Priority is server-declared list order — no numeric field. The first eligible candidate with a matching RESUMED handler wins and the loop breaks. That's config-changeable without a client release; the cost is that the client can filter but not reorder.

Timing fields: initialDelayMillis (cooldown since lastIdleTime, deferred via a delayed re-send rather than blocking the loop), showDurationMillis (auto-dismiss → OnTimedOut), and evictIfIntervened (host pauses mid-show → evict and free the queue).

Two persistence mechanisms chosen by data shape: Proto DataStore (intervention_cache.pb) for structured counters and lifecycle status, wrapped in a ReplaceFileCorruptionHandler that logs to Crashlytics; plain SharedPrefs (InterventionPrefs) for single-boolean hot-path frequency caps. Server-driven cache invalidation comes via a clearStatusEntries field in the config response, which wipes the local status cache to reset frequency caps after a campaign change — no app update needed.

Eligibility is a standing invariant, not a one-time gate. If a counter update makes the currently active intervention ineligible mid-display, it's evicted and the loop reruns.

Hardest problem — simultaneous RESUMED screens. Multiple screens can be RESUMED at once: Home's bottom-nav chrome and a tab fragment are both alive, so two handlers claim eligibility for what looks like the same screen. Resolved by matching on intervention anchor type (BottomNavAnchorModel vs AppBarAnchorModel) rather than screen identity.

The trade-off — actor over Mutex: a mutex protects data; an actor protects a sequence of decisions. "Is X eligible" and "should X show now" both depend on full queue state, so the actor makes read-then-decide-then-write atomic by construction rather than by discipline.

Consumer example: PostInterventionUtil.kt in the feed answers only "where does this tooltip physically attach on a scrolling RecyclerView" — waits for SCROLL_STATE_IDLE, walks visible children computing a visible-height ratio, picks a post ≥50% on-screen, dispatches to the concrete ViewHolder. Pure geometry, fully factored out of the "when."

What I'd change: the candidate scan is O(candidates × handlers) per state tick — worth indexing by screen only if config grows an order of magnitude. And I'd make cross-screen priority an explicit field so a new engineer doesn't have to reverse-engineer that list order matters.

03 Performance & build

Measure, then optimize — and watch what the optimization breaks.

P05Jank fixes — ~80% reduction via recomposition scopingShareChat / Moj
The hook. Cut jank ~80% by fixing recomposition scope. State was prop-drilled from a legacy MVP presenter into Jetpack Compose across a custom AndroidView interop boundary — so every upstream state change invalidated far more of the composition tree than it needed to.

The four steps:

  1. Diagnose — profile to confirm which composables recomposed per frame versus which actually needed to. The number has to come from a tool, not a feeling.
  2. Root cause — the AndroidView interop wrapper received state as a parameter from the presenter. Compose can't see into an AndroidView to skip unaffected children, so every presenter-level emission forced the whole boundary and its subtree to invalidate.
  3. Fix — hoist state to the lowest composable that actually reads it; wrap the boundary read in remember/derivedStateOf so the interop view updates only when the derived value changes; mark state classes @Immutable/@Stable so Compose's skip check can actually fire.
  4. Verify — re-ran the same profiler to confirm 80%, not "feels smoother."

The trade-off: narrower hoisting means stricter composable contracts — explicit params instead of implicit shared-presenter reads. More boilerplate, in exchange for predictable, scoped recomposition.

Likely follow-up worth pre-empting: why remember alone doesn't fix an over-broad read — it caches a broad read, it doesn't narrow it. The fix has to change what's read, not just memoize the reading.
P06Build & CI optimization — 45–52% fasterDream11 · CriQ
The hook. Two related problems — slow Android release builds in CI, and long local Gradle cycles. Incremental APK/AAB build went from ~25–30 min to ~14–16 min (45%); the full Play Store upload workflow from ~38 min to ~18 min (52%); local incremental builds 40–60% faster. Key PR #529, with #457 (runner memory), #549/#554/#561 (caching), #855 (CI cleanup), #563 (Slack APK upload).

  + --frozen-lockfile --prefer-offline
  → cache miss ~2–3 min  vs  cache hit ~10–15 s

  ← THE SINGLE BIGGEST CONTRIBUTOR, ~5–6 min saved per build
  + gradle/actions/setup-gradle@v3

  compile Ruby 3.3.0, install Bundler, install deps)
  with ruby/setup-ruby@v1 + bundler-cache: true
  → ~5–6 min  vs  ~30–60 s

New workflow inputs: build_type (aab/apk), flavour (prod/staging),
  app_variant (local/international), clean_build, version

Telemetry: start/end timestamps exported as BUILD_TIME to
  GITHUB_ENV, surfaced in Slack with flavour, output type, result

PR checks: shared composite action setup-and-prepare, node_modules
  cached on yarn.lock, conditional install on cache hit, and
  DIFF-BASED file lists so lint/TS/asset-size run only on changes
The best story here — the second-order failure. After adding caching, the cache-save step started hanging and throwing "No space left on device." Root cause: Gradle transform caches, 2–5 GB each, being uploaded to Actions cache. The fix was a post-build if: always() cleanup that strips regenerable artifacts before save — transforms-*, build-cache-*, jdks-*, daemon, build outputs (already uploaded) — while keeping dependency-resolution caches, which compress fast and have high reuse value. Cache save went from hanging indefinitely to 0–2 min.

So: "which single change gave the biggest win?" → Gradle dependency caching, ~5–6 min. "What went wrong?" → the cache-save hang, which is the more interesting story, because the optimization created a new failure mode and the fix was diagnosing the second-order effect rather than reverting.

P07Performance tracking system — four metrics across the native/JS boundaryDream11 · CriQ
The hook. Built a four-metric performance tracking system spanning native and JS, because React Native's app-start cost is split across a boundary neither side can see alone. JS simply can't observe when the process actually started.

The four events: Performance_AppStart, Performance_ScreenLoad, Performance_ScreenTransition, Performance_BundleLoad.

Why it needed native modules:

Android:
  MainApplication.kt onCreate() captures System.currentTimeMillis()
    into a static
  → new PerformanceTrackerModule.kt exposes getNativeAppLaunchTime()
    to JS, registered in BridgeModules.kt

iOS:
  mirrors from AppDelegate.swift via an Obj-C module
    + Swift bridge helper + bridging-header import

JS stitches it together (performanceTracking.ts, a singleton):
  native launch time → bundle load start/end → RN init
    → component mount → markAppReady()
  = a real TTI number

Screen load and transition are RN-side: AppNavigator.tsx marks first render on navigation-container ready and subscribes to state changes to diff previous vs current route for transition timing. An optional useScreenPerformanceTracking hook uses useFocusEffect for per-screen granularity.

The judgment call worth narrating: I didn't just build custom tracking — I decided what each of three sources is for. Custom tracking for the detailed breakdown and screen-level metrics. Firebase Performance for automatic cold/warm/hot start, network requests, and dashboards without building my own. Play Console Android vitals for real production TTFD/TTI with device and OS breakdowns plus ANR/crash correlation. And I named the limits: Play Console is Android-only and 24–48 h delayed; Firebase's app-start markers won't match custom ones exactly. Three sources, each validating the others — that's an instrumentation strategy, not a metric.

P08Speech-to-Text — dual-engine, WebView-bridgedDream11 · CriQ
The hook. STT in CriQ isn't used from native RN screens at all — it's fully bridged through CriqWebView so embedded web content (the Sports AI mic UI) drives it. Two parallel engines: Android's native SpeechRecognizer on-device, and a GCP streaming path over Socket.IO that works on both platforms. iOS has no native STT module — GCP streaming only, remote-config gated.

Path A — GCP streaming (primary, cross-platform):

1. Web: postMessage({ eventSource: 'CriQ', eventType: 'startGcpStreaming' })
2. useGcpSpeechToText requests RECORD_AUDIO
   AudioRecord.init(AUDIO_CONFIG) — 16 kHz mono 16-bit PCM, audioSource 6
3. Socket.IO connects to STT_SERVER_URL with Bearer token
   15 s connection timeout
4. emit('startStream') → AudioRecord.start()
   → chunks via emit('audioData', chunk)
5. Server → 'transcript' { text, isFinal }
   → injectJavaScript → window.sendTranscriptGcp(text)
6. Silence: server 'silenceDetected' OR client-side
   SILENCE_TIMEOUT (2000 ms) fallback → window.onSilenceDetected()
7. stopGcpStreaming → stop audio, emit('endStream'),
   window.isStreaming(false)

Path B — native Android SpeechRecognizer: checkAudioPermission() → requestAuthorization() → initialiseSpeechRecoginition() → startListening() (returns a Promise resolving with final text) → partial results streamed via DeviceEventEmitter 'onSpeechPartialResult' → stopListening() → destroy() on unmount. Uses LANGUAGE_MODEL_FREE_FORM, en-US, EXTRA_PARTIAL_RESULTS = true, 3000 ms complete-silence / 3000 ms minimum input.

Bridge contract: every web→native message must carry eventSource: 'CriQ'; every native→web response is an injected window.* callback. One clean integration point — CriqWebView.tsx.

Why two engines — the real answer. It's not redundancy for its own sake. Native Android STT is free, low-latency, and needs no network. GCP streaming gives partial/final transcripts with server-side silence detection and is the only option on iOS. The remote-config gating (GCP_STREAMING_CONFIG, IOS_STT_CONFIG, plus a micVariant Plugger experiment param) means the split is a rollout lever, not a hardcoded architecture.

Low-bandwidth handling, grounded rather than generic: audio streams in PCM chunks rather than uploading as one blob, so a weak connection degrades to slower partials instead of a failed request. There's a 15 s connect timeout, and sttError → window.sendTranscriptionError(err) so the web layer can degrade its own UI. On Android the native engine is a genuinely offline-capable fallback path.

Error handling to name: logNonFatalError for GCP errors; Android codes ERROR_AUDIO_SPEECH_PERMISSION, ERROR_DENY, ERROR_PERMANENT_DENY mapped to human-readable messages; startListeningToSpeech's catch sends an empty transcript rather than throwing into the WebView.

What I'd change: en-US is hardcoded in SpeechToText.kt. For an India-first product that's the first thing to parameterize.

P09ML on Edge — client SDK + model delivery serviceDream11
The hook. A platform for running ML models on-device — a TypeScript client SDK that manages model download, runtime inference, and an on-device event store, plus a backend service that decides which model version each device should be running. This is the strongest platform design story, distinct from CriQ's product work.

SDK side (MLOnEdgeInterface), four components:

ComponentResponsibility
RuntimeInterfaceloadModel/loadModelasync, predict/predictAsync, destroy/destroyAsync
DynamicFeatureInterfaceon-demand install, deferred install, uninstall, getIsModuleInstalled, cancelInstall, plus mockInstallSuccess/mockInstallFailure
ModelDownloaderInterfacedownloadModels(modelIds) → PromiseSettledResult<MLModel>[], getModelFileLocalPath
EventStoreInterfacemlDBInit, insertEventData, clearEventsTableData

Three details worth calling out unprompted:

  • PromiseSettledResult, not Promise.all — a partial model-download failure doesn't nuke the whole init. Deliberate choice.
  • Mock install hooks are part of the public interface. The DFM install path is the hardest thing to test on a real device; baking mocks into the interface is testability designed in, not bolted on — the same DFM boundary problem solved with reflection at ShareChat, solved here with an explicit test seam.
  • DownloadConfig carries concurrency, downloadTimeOut, and a RetryConfig with RetrialPolicy: LINEAR | EXPONENTIAL | JITTER_EXPONENTIAL. The jitter is there to stop every device retrying in lockstep after an outage — a thundering-herd answer, and a good one to volunteer.

Service side: the client sends the model info it currently has; the service returns anything newer. GET /v1/client/models?mlModels=<name> returns modelId, version, fileSize, packageHash, a signed CloudFront downloadURL, and an eventSchema containing literal CREATE TABLE IF NOT EXISTS ... statements plus per-event column mappings with defaultVals and expiryInSecs. Headers carry App-Version, Codepush-Version, Build, Platform — so model compatibility resolves server-side against the exact client build.

The part interviewers like most — a CI pipeline for a model, not for code. A model isn't just uploaded; it moves through a state machine: Validating Events → Feature Compute Validating → Creating Artifact → Ready to Run CI → Running CI → Ready to Publish → Live, with explicit failure states at each stage and field-level freeze rules. CI here means: spin up infra, retrieve artifacts, start emulators, download the model artifact via the SDK, load it, run inferences, and diff against a stored test-case file. That's the cleanest evidence of treating ML as a shipped artifact with a release process, not a notebook.

Model selection evidence — the ONNX benchmark. Load time, inference time, and memory across MobileNetV2 (13.3 MB), ResNet18/34/50/101/152, and PHI-3 (1.7 GB), on a real low-end device (Samsung A3core, Android 11, 2 GB RAM) vs a 4 GB emulator, 10 iterations each:

MobileNetV2501 ms185 ms176 ms20 ms
ResNet18601 ms372 ms456 ms61 ms
ResNet341349 ms726 ms700 ms118 ms

ResNet101 and above simply don't run on the phones a large share of Indian users actually have, and PHI-3 needs 2.3 GB on first load. That's an argument for MobileNetV2-class models made with data from the target device, not from a benchmark table.

Known characteristic worth naming rather than glossing over: memory drops meaningfully on second load (e.g. 170 MB → 116 MB for MobileNetV2), suggesting first-load allocations aren't fully released.

P10Computer vision POCs — ball tracking & player detectionRC / DreamPlay
The hook. An engineering initiative to learn applied ML by shipping real systems rather than notebooks — four POCs across ball tracking, player detection, and match analytics, each with labeled data, a trained model, an inference pipeline, and honest evaluation metrics.

The arc — narrate as a progression, because that's the whole value:

  • POC 0 — YOLO + OpenCV: frame extraction → YOLO per frame → bbox center → trajectory. Result: badly broken trajectory. YOLO has no temporal context for small, fast, motion-blurred objects. This is a documented false start, and it's an asset — it's the evidence for why the move to a specialized time-aware model was necessary.
  • POC 0b — modular analytics prototype: court calibration via homography, players via YOLO + ByteTrack, ball pivoted to TrackNet, events via heuristic bounce/shot-proximity/NVZ rules. ~85% player detection, ~50% shot recall, no labeled event data. Explicitly labeled a feasibility study, not production.
  • POC 1 — ball tracking, end to end: TrackNetV2 (fully-convolutional U-Net with skip connections), input = 3 consecutive RGB frames stacked channel-wise (batch, 9, 288, 512), output = 3 heatmaps. Pre-trained on badminton; I built an OpenCV labelling GUI, hand-labeled 1,030 frames, and fine-tuned on Colab — last 14 conv layers unfrozen, Adadelta, lr 0.01, batch 10, 20 epochs, 70/30 split, heatmap sigma 2.5, 15 px TP tolerance.
  • POC 2 — player detection & identity: RF-DETR detector (batched, court-ROI filtered) → BoT-SORT tracker with per-rally reset (Kalman + Hungarian) → Vertex AI VLM (Gemini) on keyframe crops for identity → auto-detects singles vs doubles → annotated video + player_detections.json.

The inference pipeline (run_pipeline.py, ~1,400 LOC) — this is the engineering:

• Batched inference (N 3-frame windows per GPU call)
• @tf.function graph compilation
• Threaded video reader decoding + preprocessing while GPU runs
• OpenCV instead of PIL for preprocessing
• Single-pass mode (inference + trajectory video in one video read)
• GPU OOM auto-recovery — recursively halves batch and retries
• Three-tier CPU fallback (tf.function → eager → model.predict)
  for the macOS NCHW MaxPool case

Post-processing knobs that tune quality with NO retraining:
  --heatmap-threshold, --min-confidence,
  --smooth-window (temporal median filter),
  --max-jump-frac (reject physically impossible jumps)

Results — lead with the honest read, not the number. 88,920 frames in ~49.5 min at 29.9 FPS end-to-end. On the 1,030 labeled frames: precision 79.6%, recall 38.3%, F1 51.7%, accuracy 58.3%.

The analysis is the answer. Precision is strong (when it fires, it's right — only 2.2% wrong-location), false positives are low (3.5%), and recall is the bottleneck (371 missed of 1,030). Causes: motion blur below the heatmap threshold, a ball only a few pixels wide at broadcast distance, outdoor lighting, limited labeled data, and a badminton→pickleball domain gap. Conclusion: more labeled data fixes this, not architecture changes. Saying that — and resisting the urge to tune the model instead of the dataset — is the senior signal.

Debugging stories, all real: Keras 3 / TF 2.16 TFSMLayer load failure (SavedModel is Keras 2 format) → tf-keras compat package; GPU OOM at batch 32 → default 8 with auto-split; unplayable mp4v output → auto-remux to H.264 via ffmpeg with MJPG fallback; and F1 = 0% on the first run → wrong video matched to the labels, fixed alignment. That last one is the best one to tell: a metric of exactly zero is a data-plumbing bug, not a model bug, and recognizing that instantly is a real skill.

The line that lands it: "most of the effort was integration and reliability, not model selection."

P11AI Test Generator Agent + PR Reviewer — with a real eval strategyDream11 · CriQ
The hook. A diff-driven agent that writes Jest unit tests for changed TypeScript in a React Native codebase — runs locally via CLI, in Cursor via a rule file, and in CI when a PR gets the generate_tests label. It doesn't just generate; it validates through TypeScript, ESLint, and Jest, and self-heals up to 5 attempts before it's allowed to commit. PRs #893 (agent + cursor rules), #915 (generated tests).

The pipeline, in order:

1. Diff parse — git diff main...HEAD, filter to testable files
   (in src/, .ts/.tsx, not __tests__, not .test., not .d.ts)

2. AST parse (@typescript-eslint/parser, NOT regex) — extracts
   function declarations, arrow functions, class methods with
   name, line span, params + types, return type, source, exports
   → maps changed line ranges onto function spans

3. Semantic change classification — new_function, logic_change,
   new_branch, removed_branch, param_change, return_change,
   error_handling, refactor

4. Skip decision (the cost gate) — skip only if 3+ existing tests
   AND no semantic change AND no diff AND no --force

5. Multi-layer reference system (the interesting design):
   L1 curated templates per category      ~400–500 tokens
   L2/3 gold-standard + 4 truncated real examples  ~600–900
   L4 mock patterns (RN/nav/storage/analytics)     ~200–300
   L5 domain patterns (sports/cricket data)        ~100–200
   → 7–10 reference files per generation, deliberately budgeted

6. Prompt construction — role, analysis instruction, function
   details, semantic changes, existing tests, references,
   imports, critical rules, output format

7. Generation — Cursor CLI (default, sonnet-4.5) / Anthropic /
   OpenAI, provider auto-selected by env key present

8. Post-processing — strip markdown, extract describe blocks,
   ensureBalancedBraces(), write to *.test.new.ts so nothing is
   overwritten without review; merge imports; clean up describe
   blocks for deleted functions; rename orphans to *.deleted

9. Three-stage validation — tsc --noEmit (0 errors),
   ESLint (0 errors), jest --coverage with ≤20% failure rate

10. Self-heal — attempt 1 generates, 2–5 fix. The fix prompt
    carries the test file, source file, and every parsed error
    with type, line, message, and Expected vs Received values.
    After 5: report failure, don't commit.

11. Report — commit to PR branch, post coverage comment,
    remove the generate_tests label

Two prompt-engineering decisions worth naming:

Behavioral over mechanical. The prompt explicitly bans tests like "should call API with correct URL" in favor of "when match is in PreToss state, should return null as stats unavailable." Target ratio 70% behavioral / 30% edge cases. The insight: a mechanical test asserts the implementation you just wrote, so it passes forever and catches nothing. A behavioral test asserts the contract, so it fails when the contract breaks. LLMs default hard toward mechanical, and the prompt has to actively push against it.

Trace-before-you-write. Rules include mentally executing the function per test case, matching exact output format (commas, units, empty string vs null), type-safe test data (@ts-expect-error rather than passing null into a string param), lint-safe code (jest.mocked(), no bare require()), no markdown in output, and brace counting to zero. Each exists because it was a real observed failure mode.

Metrics: ~1 minute per function vs 35–75 manual. Coverage targets: lines 80%, functions 90%, branches 60%, statements 80%.

The trade-off to volunteer: a ≤20% test failure threshold is not "all tests pass." It's a deliberate throughput/quality trade — the agent's output is a reviewed starting point (hence .test.new.ts), not merged truth. If asked "isn't 20% failures bad?", the answer is that the alternative is 0% coverage on files nobody had time to test, and every generated test still goes through human PR review. But be ready for the pushback: that threshold silently normalizes broken tests if nobody reads the report.

How to evaluate an AI skill — three layers. This is the question that actually gets asked: "how do you know it's any good?"

Layer 1 — deterministic gates. Does it compile? Does it lint? Do tests execute, failure rate ≤20%? Cheap, binary, run every time. They tell you the output is valid, not that it's good.

Layer 2 — an offline eval set. A frozen set of ~30–50 (diff → expected test characteristics) pairs drawn from real merged PRs, including the awkward ones: a pure refactor with no behavior change, a new error branch, a hook with async state, a component with navigation mocks, a deleted function. Mutation testing is the answer to give if you only give one. Coverage says a line was executed; mutation says the test would actually notice if that line were wrong. For a generated suite this distinction is everything, because LLMs are very good at producing tests that execute code and assert nothing meaningful.

Layer 3 — production signal. Adoption rate (how many PRs use the label), human edit distance on generated tests before merge (if reviewers rewrite 80%, the agent is net-negative), and the one that matters most: do escaped bugs land in files the agent covered? That closes the loop back to why unit tests exist at all.

For the PR reviewer specifically, the eval shape differs because there's no compiler oracle:

  • Precision over recall, deliberately. A reviewer bot that comments on everything gets muted within a week; one that comments rarely and is right stays trusted.
  • Build the labeled set from history — past PRs where a human left a substantive comment are your ground truth.
  • Track comment resolution rate — what fraction of the bot's comments led to a code change vs were dismissed. Closest thing to real-world precision, and it's already in your PR data.
  • Watch the failure mode nobody measures: reviewers rubber-stamping because "the bot looked at it." Automated review can reduce human scrutiny, which is a net loss even if the bot is decent.
The SDLC framing to say out loud: "The pattern across both agents is the same — deterministic pre-processing to build clean context, an LLM for the genuinely fuzzy step, a deterministic verifier as the oracle, a bounded repair loop, and a human gate before anything merges. AI is a step inside the pipeline, not a replacement for the pipeline. The compiler, the test runner, and the reviewer are all still there, and they're what makes it safe to let a model write code at all." And the honest caveat: the acceleration is real — the CV work moved roughly 5× faster with AI pair-programming, and test generation went from 35–75 minutes a function to about one — but every goal, quality bar, and trust decision stayed with the engineers.
