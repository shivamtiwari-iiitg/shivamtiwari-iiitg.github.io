01 The DSA round

Usually the first gate. The bar is blunt: solve at least one medium independently, and be able to explain every line.

R01What actually gets scored in a DSA screenStrategy
In plain terms. Two things are scored separately: did you reach a working solution, and can you explain it. Failing the second is worse than a partial solution on the first — an unexplainable correct answer reads as memorised.
✅ Passes❌ Rejects
Solve a medium independentlyNo solution even after hints and extended time
Think aloud — narrate the approach even when partialWorking code you can't explain line by line
State complexity before codingConfidently brute-forcing when a better solution exists
Handle edge cases unpromptedAsking to code in something other than the role's language
Self-correct out loud when you spot a flawGoing silent for minutes while stuck
The one rule that matters: never go quiet. An interviewer can't score silent thinking. Narrate the dead ends too — "I considered a hashmap here but the ordering requirement kills it, so I'm going with a heap" is scored positively even if you then need a hint.
R02The pattern list worth drilling (and the ones that actually appear)Strategy
In plain terms. Mobile-role DSA screens skew heavily toward arrays, strings, hashmaps and trees. Graphs and DP appear but usually as the harder second question. Design-flavoured problems (LRU, rate limiter) show up disproportionately because they double as an Android/systems signal.
PatternWhy it appears
Hashmap + frequency countingThe most common medium shape by far
Two pointers / sliding windowSubstring, subarray, and "longest/shortest X" problems
Trees — BFS/DFS, level orderRecursion fluency check
Heap / priority queueTop-K, merge-K, scheduling
Graph BFS/DFSGrid/island problems, dependency resolution
LRU cacheAppears constantly in mobile rounds — it's DSA and a caching-design signal
Dynamic programmingLess common, but a strict panel may fail you outright without it

Why LRU deserves special drilling: it's the one problem where a mobile interviewer can pivot straight from "implement it" to "now where would you use this in an app?" — and the answer connects to image caching, the memory tier of a repository, and bitmap eviction. Both implementations are worth knowing cold:

// Approach 1 — LinkedHashMap with accessOrder=true (simplest)
class LRUCache(private val capacity: Int) :
    LinkedHashMap<Int, Int>(capacity, 0.75f, true) {   // true = access order
    override fun removeEldestEntry(eldest: MutableMap.MutableEntry<Int, Int>) =
        size > capacity
}

// Approach 2 — manual HashMap + doubly linked list, O(1) get/put
class LRUCache(private val capacity: Int) {
    private class Node(val key: Int, var value: Int) {
        var prev: Node? = null; var next: Node? = null
    }
    private val map = HashMap<Int, Node>()
    private val head = Node(0, 0)   // dummy head = most recent
    private val tail = Node(0, 0)   // dummy tail = least recent
    init { head.next = tail; tail.prev = head }

    private fun remove(n: Node) { n.prev?.next = n.next; n.next?.prev = n.prev }
    private fun addFirst(n: Node) {
        n.next = head.next; n.prev = head
        head.next?.prev = n; head.next = n
    }

    fun get(key: Int): Int {
        val node = map[key] ?: return -1
        remove(node); addFirst(node)      // touch = move to front
        return node.value
    }

    fun put(key: Int, value: Int) {
        map[key]?.let { remove(it) }
        val node = Node(key, value)
        map[key] = node; addFirst(node)
        if (map.size > capacity) {
            val lru = tail.prev!!
            remove(lru); map.remove(lru.key)   // evict from the back
        }
    }
}

Edge cases to walk through unprompted: capacity of 1; re-inserting an existing key (must update value and move to front, not duplicate); get on a missing key; eviction when put causes overflow. Naming these before being asked is the differentiator.

02 Machine coding

60–120 minutes to build something functional from a design and an API spec. Scored on structure as much as completion.

R03How to run a 120-minute machine coding roundStrategy
In plain terms. The trap is opening the editor immediately and coding for 120 minutes. The candidates who pass spend the first 15 minutes scoping and the last 15 defending — because a smaller, clean, complete thing beats a sprawling half-built thing every time.

Phase the time explicitly:

Pre-coding   (15 min)  Clarify requirements, name edge cases,
                       agree the scope you'll deliver.
                       Say out loud: "I'll build A, B, C fully;
                       D I'll stub and explain."

Coding       (90 min)  Skeleton first, then fill in.
                       Folder structure → types → state layer
                       → components → wire up → polish.

Post-coding  (15 min)  Demo against the acceptance criteria,
                       defend structure, name what you'd do
                       with more time.

What's actually being scored:

  • Functional completeness of the scope you agreed — not the maximum possible scope.
  • Modular topology — low coupling, clear file boundaries. A single 600-line component fails even if it works.
  • State resilience — domain state isolated from UI views, so state survives re-render and could be tested headlessly.
  • Edge-case handling — empty state, loading state, error state. Shipping only the happy path is the most common silent failure.
The five moves that separate a pass: (1) clarify before writing a line; (2) announce the structure before coding it; (3) write the skeleton first and fill in details; (4) say "I'd normally reach for library X here" for anything you don't know by heart rather than stalling; (5) proactively raise trade-offs and what you'd optimise next. That last one is the volunteer-trade-offs habit — it applies here as much as in system design.

Typical prompts: a mini expense-splitter with a settlement calculation engine; an image gallery grid with lazy loading and fluid updates; an infinite paginated list with search and filters; a multi-step form with validation. All of them reward the same skeleton.

R04The skeleton to start every React Native machine coding round withTemplate
In plain terms. Have a structure you can lay down in five minutes without thinking. That buys you the whole 90 minutes for the actual problem, and it demonstrates the modular topology being scored.
src/
  api/          client.ts, endpoints.ts     ← network only
  types/        models.ts                   ← shared types first
  store/        useFeedStore.ts             ← domain state, UI-free
  hooks/        usePagination.ts, useDebounce.ts
  components/   FeedItem.tsx, EmptyState.tsx, ErrorState.tsx
  screens/      FeedScreen.tsx              ← composition only
  utils/        format.ts

Three hooks worth having memorised — they cover most prompts:

// 1. Pagination — the backbone of any list prompt
function usePagination<T>(fetchPage: (cursor?: string) => Promise<{items: T[]; next?: string}>) {
    const [items, setItems] = useState<T[]>([]);
    const [cursor, setCursor] = useState<string | undefined>();
    const [loading, setLoading] = useState(false);
    const [done, setDone] = useState(false);

    const loadMore = useCallback(async () => {
        if (loading || done) return;          // guard double-fire
        setLoading(true);
        try {
            const page = await fetchPage(cursor);
            setItems(prev => [...prev, ...page.items]);
            setCursor(page.next);
            if (!page.next) setDone(true);
        } finally { setLoading(false); }
    }, [cursor, loading, done, fetchPage]);

    return { items, loadMore, loading, done };
}

// 2. Optimistic mutation — likes, favourites, any toggle
function useOptimisticToggle(initial: boolean, commit: (v: boolean) => Promise<void>) {
    const [value, setValue] = useState(initial);
    const toggle = async () => {
        const next = !value;
        setValue(next);                       // optimistic
        try { await commit(next); }
        catch { setValue(!next); }             // rollback on failure
    };
    return [value, toggle] as const;
}

// 3. Viewability — which item is on screen (autoplay, analytics)
const viewabilityConfig = { itemVisiblePercentThreshold: 60 };
const onViewableItemsChanged = useRef(({ viewableItems }) => {
    setActiveId(viewableItems[0]?.item?.id ?? null);
}).current;   // MUST be a stable ref — RN throws if this changes identity
The useRef on onViewableItemsChanged is a real gotcha — React Native throws "Changing onViewableItemsChanged on the fly is not supported" if you pass a new function identity across renders. Knowing that without looking it up is a strong production signal.

03 Depth & LLD rounds

Where Android/RN knowledge is probed two layers past the textbook answer — and where LLD can offset a weak coding round.

R05Going two layers deep — the actual bar in a depth roundStrategy
In plain terms. Every answer gets a follow-up. The first answer establishes you know the term; the second and third establish whether you've actually shipped it. Interviewers explicitly probe until you run out of depth — so the goal is to not run out at layer one.

What "two layers deep" looks like on one question:

Q: "What happens if you block the main thread?"

L1 (textbook, insufficient):
   "It causes an ANR."

L2 (mechanism — this is the real answer):
   "The main thread runs a Looper pulling from a MessageQueue.
    Blocking it means input, draw and lifecycle callbacks
    stop being dispatched. After ~5s of undelivered input
    the system raises an ANR; ~10s for a foreground broadcast."

L3 (production — what separates senior):
   "In practice I catch these with StrictMode in debug for
    accidental main-thread disk/network I/O, and diagnose
    real ones from /data/anr/traces.txt plus Play Console
    ANR vitals, which give the stack at the freeze."
The pattern to internalise: what → how it works underneath → how I've dealt with it in production. Prepare layer 3 for every topic you claim on your resume, because that's the layer that can't be memorised from a blog post — and interviewers know it.

Two behaviours that get rejected here: giving textbook definitions without mapping them to a real scenario, and freezing when told "tell me more about that." If you genuinely don't know, reasoning aloud toward an answer scores far better than guessing confidently or going silent.

R06KMM — where the shared boundary actually sitsAndroid
In plain terms. KMM shares business logic, not UI. The interview failure mode is defining it as "shared Kotlin code" and stopping — the real question is always where you draw the line and why.

What goes where:

LayerShared?Why
UI (Compose / SwiftUI)NoPlatform idioms differ; sharing UI is where cross-platform gets a bad name
ViewModel / presentationSometimesShareable, but lifecycle differs — often a thin platform wrapper over shared state
UseCase / business rulesYesPure Kotlin, no platform deps — the sweet spot
RepositoryYesInterface shared; some impls need expect/actual
Networking (Ktor)YesKtor has multiplatform engines
Persistence (SQLDelight)YesGenerates typed Kotlin for both platforms
Platform APIs (keychain, camera, push)Noexpect/actual — declare shared, implement per platform
// commonMain — the shared declaration
expect class SecureStorage {
    fun save(key: String, value: String)
    fun read(key: String): String?
}

// androidMain — EncryptedSharedPreferences
actual class SecureStorage(private val ctx: Context) {
    actual fun save(key: String, value: String) { /* Keystore-backed prefs */ }
    actual fun read(key: String): String? = /* ... */
}

// iosMain — Keychain
actual class SecureStorage {
    actual fun save(key: String, value: String) { /* Security framework */ }
    actual fun read(key: String): String? = /* ... */
}

Designing a shared profile screen — the answer shape: share the ProfileUseCase, ProfileRepository, the DTO→domain mapping, validation rules, and the state model. Keep the rendering native on both sides, and expose shared state to iOS through a wrapper because Kotlin Flow doesn't consume idiomatically in Swift without one (SKIE or a callback wrapper).

The honest trade-off to volunteer: KMM buys you one implementation of business rules and one place for bugs to be fixed — at the cost of a more complex build, a smaller hiring pool, and iOS engineers debugging Kotlin. It's a good fit when logic is heavy and UI is thin; a bad fit when the app is mostly UI with a thin logic layer.

R07The LLD prompts that recur — and how to structure the answerAndroid · RN
In plain terms. LLD is about ownership boundaries — which class owns what state, and how they talk. The recurring prompts are all variations of "design a component that manages a shared resource under concurrency and lifecycle pressure."

The prompts that keep appearing:

  • Notification manager — scheduling, deduplication, priority queueing, lifecycle awareness. (This is the Interventions Framework problem in disguise — same arbitration shape.)
  • Image caching layer — memory tier, disk tier, eviction policy, concurrent access, request dedup, cancel-on-recycle.
  • An SDK used by multiple host apps — initialization contract, threading guarantees, lifecycle binding, no assumptions about the host's DI.
  • State management for a real-time feature — explicit state machine, event flow, error recovery, reconnection.
  • Multi-step form — a finite state machine over steps, per-step validation, resumability.

Structure every LLD answer the same way:

1. Clarify   — scale, lifecycle, threading, offline, failure modes
2. Entities  — name the classes and what each OWNS
               (ownership is the actual subject of the round)
3. Contracts — the public interface, method by method
4. Data flow — one concrete request traced end to end
5. Concurrency — what's shared, what serializes it
6. Failure   — what happens on error, cancel, or kill
7. Testing   — where the seams are, what you'd fake
The step most candidates skip is 7. Naming the test seam — "this interface exists so I can fake the downloader in tests" — is a strong senior signal, and it's exactly the reasoning behind putting mock install hooks in the ML-on-Edge SDK's public interface.

Fully worked versions of the image loader, notification/push, analytics SDK and overlay-arbitration designs are on the System Design page.

04 Stories & behavioral

The round that decides level. Prepared, specific, numbered stories — not improvised ones.

R08The three stories to have ready — mapped to real projectsEssential
In plain terms. Three stories cover almost every behavioral and senior-bar question asked. Prepare them as three-minute spoken answers, practised aloud, with numbers. Improvising here is the single most common reason strong engineers get down-levelled.

Story 1 — Architecture decision. A trade-off you made, why, and what happened. Format: constraint → options considered → choice made → engineering-metric outcome. Explicitly not a feature-delivery story.

Anchor: Interventions Framework (ShareChat)

Constraint  Overlays from many teams collided; no shared frequency
            cap; no single owner of "what shows when."
Options     (a) a Mutex-protected shared queue
            (b) per-feature local rules with a convention
            (c) a single serialized actor owning all decisions
Choice      (c) — because "is X eligible" and "should X show now"
            both read full queue state. A mutex protects data;
            an actor protects a SEQUENCE OF DECISIONS, making
            read-then-decide-then-write atomic by construction.
Outcome     One overlay at a time app-wide, no locks, adopted
            across features; config-changeable without a release.
Hindsight   Cross-screen priority should have been an explicit
            field, not implied by server list order.

Story 2 — Performance problem. A real metric moved. Numbers are mandatory, and the diagnostic process matters more than the fix.

Anchor: Build & CI optimization (Dream11 / CriQ)

Problem     Release builds ~25–30 min; full Play Store workflow
            ~38 min. Nobody owned build time, so nobody fixed it.
Diagnose    Measured where time actually went before changing
            anything — dependency resolution, Ruby setup, and
            repeated yarn installs dominated.
Fix         Three layers: Gradle (parallel, caching, config cache,
            Jetifier off), Fastlane (removed a redundant yarn
            install, added --parallel --build-cache), and Actions
            (Gradle + Yarn caches, ruby/setup-ruby).
Result      Build 25–30 → 14–16 min (45%); workflow 38 → 18 min
            (52%); local incremental 40–60% faster.
Twist       The optimization CREATED a failure: 2–5 GB Gradle
            transform caches made the cache-save step hang with
            "No space left on device." Fixed by stripping
            regenerable artifacts before save — kept dependency
            caches, dropped transforms/daemon/build outputs.

Story 3 — Something built 0→1. Your architectural decisions, not the team's. Be able to defend every choice and name what you'd change.

Anchor: CriQ (Dream11)

Scope       0→1 across Android + iOS via React Native, backend
            services, CI/CD and release pipelines — two markets
            with separate builds and sign-in.
Decisions   Native modules in Kotlin/Swift for on-device ML and a
            dual-engine STT layer, so heavy work stays native and
            only results cross to JS — keeping the JS thread free.
Why two     Native Android STT is free, low-latency and offline-
STT engines capable; GCP streaming gives server-side silence
            detection and is the ONLY option on iOS. Remote-config
            gated, so the split is a rollout lever not a hardcode.
Hindsight   en-US is hardcoded in SpeechToText.kt — for an
            India-first product that's the first thing to fix.
Why these three: "most complex problem you've solved" must be an architecture or design decision, never a debugging war story — debugging reads as mid-level. Story 1 answers that. Story 2 answers anything about impact, metrics or ownership of shared pain. Story 3 answers scope, autonomy and end-to-end delivery.
R09The behavioral prompts, and how to answer without waffleBehavioral
In plain terms. Behavioral questions cluster into five themes. Have one specific, named incident per theme — with what you actually said or did, not a description of your general approach. "I usually try to..." is the tell that you don't have a real example.
ThemePrompt shapeAnchor to use
Conflict / disagreement"Tell me about a technical disagreement"Actor vs Mutex; the ≤20% test-failure threshold; Jetifier off
Ownership / initiative"Something you did that nobody asked for"CI build time — nobody owned it, which is why it stayed broken
Receiving pushback"A time you were wrong / got hard feedback"The YOLO ball-tracking false start; F1=0% turning out to be a data bug
Ambiguity / failure"A project that didn't go as planned"Cache-save hang — the fix that created a new failure mode
Prioritization"Too much to do, not enough time"Scoping the CV POCs; picking MobileNetV2 over larger models

The structure that keeps answers tight:

Situation   1–2 sentences. Enough context, no more.
Tension     What made it hard or contested. THIS is the story.
Action      What YOU specifically did — "I" not "we".
Result      What changed, with a number where one exists.
Reflection  What you'd do differently. Always include this.
On disagreement questions specifically: the best answers end with a decision and a working relationship, not a victory. "We disagreed on the retry threshold, I laid out the failure math, we landed on a lower number than I wanted with a monitor to revisit it" scores higher than "I convinced them I was right." Interviewers are checking whether you can be overruled without being difficult.

Two traps: claiming resume ownership you can't defend under discussion, and answering like a mid-level engineer when your years say senior — the bar scales with experience, so at 5+ years you're expected to have opinions, not just knowledge. Say "we tried X and here's what broke" rather than reciting best practice.

R10What changes at Staff / SDE-4 scopeStaff
In plain terms. Senior is judged on building the thing well. Staff is judged on the decision quality around the thing — quantified trade-offs, migration paths that don't freeze delivery, and modelling how it fails before it does.

The four shifts interviewers listen for:

  • Quantify trade-offs instead of asserting them. Not "FlashList is faster" but "FlashList recycles rather than mounting/unmounting; on our list that moved p90 frame time from X to Y at a cost of one more dependency and a migration for every custom row." Dimensions worth costing: frame time, memory, bundle/binary size, developer velocity, maintenance burden.
  • Cross-functional ownership. The API payload shape, CDN caching policy, and client storage design are one decision, not three. A staff answer crosses the client/backend line — e.g. "we changed the feed payload so the client didn't need a second round trip per card."
  • Migration blueprints. Any real codebase is brownfield. Have a concrete incremental path — bridge → JSI, FlatList → FlashList, Views → Compose — that ships continuously rather than a rewrite branch. Name the strangler pattern: new surfaces on the new thing, old surfaces migrated on touch, with both coexisting.
  • Failure-mode projection. Model edge failures explicitly before shipping: OTA bundle corruption, signing-key rotation lockout, storage exhaustion, token-refresh stampede. Each with a mitigation and a business impact.
The clearest staff signal in my own work is the cache-save hang: an optimization that created a second-order failure, diagnosed rather than reverted, with the fix distinguishing regenerable artifacts from expensive-to-rebuild ones. That's the shape of thinking the level is testing for — not "I made it faster" but "I made it faster, here's what that broke, and here's the reasoning that separated what to keep from what to drop."
